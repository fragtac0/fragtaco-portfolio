# Audit tools

Headless Chrome, driven over the DevTools protocol, for screenshots and measurements. Used for the 11 November 2026 audit and for the before and after comparison. The in-app browser pane does not animate while its window is hidden; this does.

```bash
# against the dev server (default) or any URL
BASE=http://localhost:5178 node scripts/audit/cdp.mjs scripts/audit/capture-desktop.json /tmp/out
BASE=https://fragtaco-portfolio.vercel.app node scripts/audit/cdp.mjs scripts/audit/capture-phone.json /tmp/out-phone
# contact sheet from some of the shots
scripts/audit/sheet.sh /tmp/out sheet-loader 4 480 300 load-0500 load-1200 load-2100 load-2800
```

- A steps file is a JSON list. Each step may set the screen (`size`, `dpr`, `mobile`, `touch`), emulate (`reduce`, `net`, `nocache`, `cpu`), navigate (`go`), `wait`, send input (`key`, `click`, `move`, `sweep`, `tap`, `drag`), run code in the page (`eval`, printed with its `label`) and take a screenshot (`shot`).
- Headless screenshots can lag one frame behind. Take a throwaway shot first (the `-warm` names) and use the one after it.
- Each run uses a fresh browser profile in the output folder, so nothing is cached.
- Shots whose names start with `local-` show YouTube thumbnails or book covers. Never commit those; they belong in `docs/redesign/compare/local/`, which git ignores.
- Step files named in the plan that are not here yet (`shelf.json`, `wall.json`, `history.json`, `nav.json`, `fonts.json`, `loader-throttled.json`, `shelf-cold.json`) are written by whoever runs that check, following the same pattern, and committed with the task.

Frame timing inside a step: evaluate a promise that samples `requestAnimationFrame` gaps for a few seconds and resolves with the worst gap and how many were over 20 ms.

- Headless Chrome does not advance timers or CSS transitions while the page is idle between steps (nothing animating). State that depends on a timer (a layer closing, a hint fading) must be read with an `eval` that polls inside the page (a `setInterval` promise), not after a plain `wait`.
- `page-change.json` (written by `make-page-change.mjs`, edit the generator and rerun it) measures a page change: home to work, back, and home to work again at 1440 by 900, dpr 2, CPU 4 times slower. A recorder started in the page before each click reads every animation frame gap from the click until 1 s after the path changes, and long-animation-frame entries say which script caused a long one. Needs the production build on :5180.
- `page-change.json` now reports, per change, the frames while the reveal animates (after the transition's `ready`; the first frame after it is the commit frame, R31, reported apart and not counted): `animMax`, `animOver34`, `animOver20`. The debug hook (set `sessionStorage["ft:debug-change"]` to `"1"`) gives `__ftChange(to)` (a change to a path), `__ftSettled()` and `__ftFinish()` (what a press during a change calls). The linear kinds and `page-change-kinds.json` / `glass-kinds.json` are gone.

## The modern web pass (Part R59)

- `web-vitals.mjs`: `BASE=http://localhost:5180 node scripts/audit/web-vitals.mjs <out.json> [runs=3] [pages]` records, per page and size (1440x900, 390x844) with a cold cache, LCP and its element, CLS, total blocking time, the long animation frames of the first five seconds with their scripts, requests and bytes by origin and type, the font files fetched, back/forward cache and the load average. Hold the timing lock. `THROTTLE=1` (150 ms, 1.6 Mbit/s), `SETTLE_MS`, `SIZES_ONLY=1440x900` and `CHROME_FLAGS` change the conditions; the record says which. Uses `chrome-lite.mjs` (its own small CDP driver, a fresh profile per run).
- `text-boxes.mjs`: `record <out.json> [pages]` and `compare <before.json> <after.json>`: the box of the text of every element, and of every spine and interface face, at 1440x900, 390x844 and 320x568, with and without reduced motion. Run it before and after anything that could move a glyph.

- `security.mjs` (Task 34): `BASE=http://localhost:5180 node scripts/audit/security.mjs <out.json>` is the proof of the security headers and the content policy on the production build. It checks each header on the document of every page, on a `?_data` response and on the two endpoints (the static files are checked against `vercel.json` by reading it: remix-serve does not apply it, a preview deploy does), that two responses have two nonces and every `<script>` of the HTML carries its response's, that a cross-site POST to `/api/page-view` is refused with 403 and the report endpoint's five answers; then a cold browser per page and size loads the page and uses it (both home boxes by button and by deep link, a book and a video opened, wall and shelf panned) and one browser per size runs every page change both ways and Back and Forward, and the run fails on any `securitypolicyviolation` event, console error, exception, failed picture or font, or a browser warning about a header. Trusted Types ships report-only (R134), so the header check expects it in `Content-Security-Policy-Report-Only` (`TT_ENFORCED=1` checks a build that enforces it). Last, the resilience cases (`security-resilience.mjs`, both sizes): a 404 first load, an element inserted at the start of `<body>` before hydration (as an extension does), and a page change whose data request answers 500; the page must not go blank, the error page must show, report-only events are recorded and enforced violations fail. The 404 page's headers and nonce are checked with the others. `SERVER_LOG=<file>` adds the report round trip (a page that breaks its policy on purpose, over `https-proxy.mjs`, and the browser's report found in the server's log). `MODE=inventory` injects `require-trusted-types-for 'script'` report-only into every document (the response is rebuilt through `Fetch.fulfillRequest`: `Fetch.continueResponse` does not make Chrome read a changed policy header) and writes the inventory (every origin and type of request, every inline script, every use of an HTML sink, every feature asked for, a scan of the source); `HEADERS_ONLY=1` runs only the header checks (a quick negative test against another build). Parts: `security-walk.mjs` (the browser walks), `security-resilience.mjs` (the three resilience cases), `security-events.mjs` (what a walk records), `security-checks.mjs` (the expected headers, written out apart from the app's own list on purpose), `security-scan.mjs` (the source scan), `https-proxy.mjs` (an HTTPS front with a throwaway certificate).
- `logo-compare.mjs`: `BEFORE=<server> AFTER=<server> node scripts/audit/logo-compare.mjs <outdir>` proves the hero's logo is the same between two builds: its markup as the server sends it and as React makes it on a page change to the home page, and a screenshot of it on a plain ground (equal hashes).

Options: `CPU=4`, `PROFILE=0` (no JavaScript sampler: it slows the page, use it to name the work and the plain run to time it), `WARM=/favicon.svg` (loads another page first: in a fresh profile the browser's own first text layout costs 70 to 230 ms in the first frame of every page, which is not the site's), `ENGINES=1` (also when the two home scenes were asked to prepare and when they were built), `WINDOW_MS`, `TOP_FUNCTIONS`, `DUMP=<file>` (the raw trace events). `vercel-headers-proxy.mjs <vercel.json> <port> [target] [rttMs]` is a local stand-in for what Vercel does to the files of `public/` (`public, max-age=0, must-revalidate` for every static file outside `/assets/`, then the `headers` rules of the given `vercel.json`; remix-serve sends `immutable` for all of them and ignores `vercel.json`), with an optional round trip per answer, and a log at `/__log`. `repeat-visit.mjs <out.json> [runs] [pages]` (BASE must be that proxy) loads each page, leaves for `about:blank` and loads it again in the same browser, and counts what the second visit asks the server for (how many requests, how many answered 304, how many for the five picture folders, and the time the page spent waiting for them).
